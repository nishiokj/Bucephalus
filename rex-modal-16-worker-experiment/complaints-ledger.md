# Experiments Package Economics Complaints Ledger

1. Modal is an executor flag, while YAML runtime validation still documents and enforces local backend names. That split makes the cost-bearing backend invisible in the package itself.
2. S3 sync is required for Modal but configured entirely through ambient env vars. The package cannot state or audit the bucket, prefix, endpoint, or credential mode that determine storage spend.
3. The support matrix effectively requires the task image and agent image to match for `agent_container` execution, so a pure input-only Rex run still has to model each case as a writable workspace image.
4. There is no first-class pre-run cost estimate for total trials, expected sandbox starts, image pulls, S3 object traffic, or materialized output bytes.
5. `scheduling.max_concurrency`, `AGENTLAB_LOCAL_WORKER_MAX_IN_FLIGHT`, and `AGENTLAB_MODAL_MAX_ACTIVE_SANDBOXES` all influence fanout, but they live in different places and are easy to misalign.
6. Case rows duplicate the same image reference ten times. A package-level runtime image parameter would reduce registry-retag churn and accidental mixed-image runs.
7. Command placeholders exist for event paths but not for trial input or result paths, which pressures users toward shell wrappers when they want a CLI that takes explicit input and output paths.
8. Package checks report validity, not economic blast radius. A check that says "this will schedule 60 Modal sandboxes at max 8 active" would prevent expensive surprises.
9. Materialization mode is chosen at run time, not pinned in the package, even though it changes local disk and object-storage costs.
10. Token and tool-call metrics can be declared after the fact, but there is no built-in budget gate that stops a run when live LLM spend crosses a configured threshold.
11. The docs prefer `matrix.cases`, but a sealed package can retain both `cases` and normalized `tasks`, causing run-time alias rejection after build/check already passed.
12. Modal S3 sync requirements are discovered at run execution time, after preflight work has already happened. The package check cannot say "this package is missing its cost-bearing storage backend."
13. S3-compatible providers such as Cloudflare R2 still have to be threaded through AWS-named env vars (`AWS_ACCESS_KEY_ID`, `AWS_SECRET_ACCESS_KEY`, `AWS_REGION`), which hides the actual storage vendor and makes credential provenance harder to audit.
14. The generated Modal launcher passes `CloudBucketMount.key_prefix` values without trailing slashes, while current Modal SDKs require directory prefixes to end in `/`. The package check does not catch this compatibility break, so a run can pass preflight and then fail only when the Modal sandbox is created.
15. Modal `CloudBucketMount` can fail hard against an S3-compatible provider such as R2 by creating a sandbox ID and then shutting the sandbox down before any file operation. AgentLab needed a separate Modal-filesystem transfer fallback, which should be visible in package checks and cost/audit output.
16. Provider credentials are validated only when the paid remote schedule is already underway. A dummy OpenAI key can launch every Modal sandbox and then fail every trial with 401s; the package should support a credential-only dry run before spending sandbox startup time.
17. The no-source-change path depends on the native Modal CloudBucketMount behaving correctly for the chosen S3-compatible provider. When R2 fails at mount startup, the package has no declarative fallback transport, so the user is forced to choose between changing storage vendors and changing runner code.
18. The runner checks that S3 env vars exist, not that the S3 credentials can list or put objects in the configured bucket. A syntactically present but unauthorized R2 key pair can pass setup far enough to spend Modal startup time before failing.
19. The environment variable names are AWS-shaped even when the storage provider is R2, which makes it easy to paste the Cloudflare account id and API token into `AWS_ACCESS_KEY_ID` and `AWS_SECRET_ACCESS_KEY` instead of the separate R2 S3 Access Key ID and Secret Access Key.
20. The package contract encourages writing agent outputs under `/agentlab/out`, but object-store mounts are not normal filesystems. A CLI that appends JSONL events can pass package checks and then fail remotely with `EPERM` because the R2-backed `CloudBucketMount` does not support append-style mutation.
